# 추가 기능 설명: 배치 · SCAN · 트랜잭션

[core-features.md](./core-features.md)의 다섯 기능 위에 얹은 세 가지 기능을
**① 없으면 어떤 문제가 생기는지 → ② 어떻게 동작하는지 → ③ 한계** 순서로 설명합니다.
코드 위치는 `src/` 기준입니다.

| 기능 | 없으면 | 해결 방식 | 코드 |
|---|---|---|---|
| 배치 (`mget` / `mset`) | 키 N개에 요청 N번 → 요청마다 붙는 고정 비용을 N번 냄 | 한 요청에 담아 한 번의 동기 실행으로 처리 | `store.js` `mget`, `mset` |
| SCAN | 키 목록을 보려면 전체를 한 번에 훑어야 해서 서버가 멈춤 | 커서로 조금씩 나눠 순회 (역순 이진 커서) | `hashtable.js` `scan`, `store.js` `scan` |
| 트랜잭션 | 여러 단계 작업의 "중간 상태"를 다른 요청이 봄 | 명령 여러 개를 끼어들기 없이 연달아 실행 | `store.js` `transaction` |

세 기능 모두 **"명령 하나가 `await` 없이 끝까지 실행된다"** 는 기존 동시성 모델
([core-features.md 3장](./core-features.md#3-동시성)) 위에 만들어졌습니다. 새 락은 하나도 없습니다.

---

## 1. 배치 (`mget` / `mset`)

### 없으면 생기는 문제
- **요청 수만큼 고정 비용을 낸다.** 키 1,000개를 읽는데 요청이 1,000번이면 HTTP 헤더 파싱, 소켓 처리, 네트워크 왕복을 1,000번 합니다. 값 자체를 옮기는 비용보다 이 고정 비용이 훨씬 큽니다.
- **일관되지 않은 읽기.** 키 3개를 따로 읽는 사이에 다른 요청이 값을 바꾸면, 서로 다른 시점의 값을 섞어서 보게 됩니다.
- **쓰기가 절반만 반영될 수 있다.** 키 10개를 하나씩 저장하다 5번째에서 실패하면 앞의 4개만 저장된 어중간한 상태가 남습니다.

### 어떻게 동작하나

**`mget(keys)` — 한 번에 읽기**

```
POST /mget  { "keys": ["a", "b", "c"] }
 → { "results": [ {key:"a", found:true, value:1}, {key:"b", found:false}, {key:"c", found:true, value:null} ] }
```

1. 모든 키를 먼저 검증합니다. 하나라도 잘못되면 **아무것도 읽지 않고** 에러를 냅니다 (`keys[1]: key must be a non-empty string` 처럼 위치 표시).
2. 한 번의 동기 실행으로 전부 읽습니다 → 읽는 도중 다른 요청이 끼어들 수 없으므로 **서로 일관된 스냅샷**입니다.
3. 결과는 요청한 순서 그대로이고, 같은 키를 두 번 넣으면 두 번 나옵니다.
4. `found: false`(없음/만료)와 `found: true, value: null`(null을 저장함)을 구분합니다.

**`mset(entries)` — 한 번에 저장 (전부 저장되거나 전부 거부)**

```
POST /mset  { "entries": [ {key:"a", value:1, ttl:60}, {key:"b", value:{x:1}, tags:["g"]} ] }
 → { "stored": 2 }
```

원자성을 만들기 위해 **세 단계로 나눠서** 실행합니다.

```
1단계  전부 검증          하나라도 잘못이면 아무것도 저장하지 않고 400 ("entries[1]: …")
2단계  공간 확인          noeviction 에서 새 키가 들어갈 자리가 모자라면 아무것도 저장하지 않고 STORE_FULL
3단계  한 번에 반영       동기 실행 → 중간 상태를 다른 요청이 볼 수 없음. AOF 에는 한 줄로 기록
```

이 구조 때문에 기존 `set` 을 "검증(`#prepareSet`)"과 "적용(`#applySet`)"으로 쪼갰습니다. 검증을 전부 끝낸 뒤에야 적용을 시작할 수 있기 때문입니다.

세부 규칙:
- 같은 키가 여러 번 나오면 **뒤의 것이 이깁니다.**
- 덮어쓰기는 자리를 새로 쓰지 않으므로 공간 계산에서 "새 키"로 세지 않습니다. 만료된 키도 자리를 내준 것으로 계산합니다.
- LRU 모드에서는 오래된 키를 축출하며 들어가므로 항상 들어갑니다. 단, **서로 다른 키 수가 `maxKeys` 자체를 넘으면** 거부합니다.
- `nx` / `xx` 는 `mset` 에서 지원하지 않습니다 (항목마다 성공/실패가 갈리면 "전부 아니면 전무"가 깨지므로). 조건부 저장이 필요하면 트랜잭션을 쓰세요.
- 한 번에 최대 **1,000개** (`MAX_BATCH`). 단일 스레드라 너무 크게 실행하면 그동안 모든 요청이 대기합니다.

### 측정 결과 (`npm run bench:batch`)

키 1,000개, 같은 머신에서 keep-alive HTTP로 측정:

| 방식 | 시간 |
|---|---|
| `GET` 을 하나씩 (순차) | 76 ms |
| `GET` 동시 50개 | 56 ms |
| **`POST /mget` 한 번** | **2.3 ms** |
| `PUT` 을 하나씩 (순차) | 111 ms |
| `PUT` 동시 50개 | 90 ms |
| **`POST /mset` 한 번** | **2.2 ms** |

약 30~50배 차이입니다. 같은 머신이라 네트워크 지연이 거의 없는 최선의 경우에도 이 정도이므로, 서버가 원격이면 요청마다 왕복 지연이 붙어 차이가 더 벌어집니다. 절대값은 머신마다 다릅니다.

> 참고: 이 PC에서는 Node 내장 `fetch`가 순차 요청 하나에 약 14.5ms의 고정 오버헤드가 있었습니다(`http` 모듈은 0.14ms). 그래서 벤치마크는 `http`로 직접 호출합니다. `MiniRedisClient` 는 아직 `fetch` 를 쓰므로 이 환경에서는 요청당 그만큼이 붙습니다. 배치가 더 유리해지는 이유이기도 합니다.

### 한계
- 한 번에 최대 `MAX_BATCH`개, 요청 본문은 1MB 이하입니다.
- HTTP `mget` 은 값만 돌려주고 TTL 은 돌려주지 않습니다 (TTL 이 필요하면 트랜잭션의 `ttl` 명령 사용).
- 배치가 커지면 그 실행 시간 동안 다른 요청이 기다립니다 (단일 스레드의 대가).

## 2. SCAN (커서 기반 순회)

### 없으면 생기는 문제
- **전체 순회는 서버를 멈춘다.** `GET /keys` 는 해시 테이블 전체를 한 번에 훑는 O(n)입니다. 키가 수백만 개면 그동안 단일 스레드가 이것만 처리하므로 **모든 요청이 대기**합니다. 운영 중인 서버에서는 못 씁니다.
- **그렇다고 페이지네이션을 단순하게 만들 수도 없다.** "0번 버킷, 1번 버킷, 2번 버킷…" 식으로 번호를 올리며 나눠 돌면, 순회 도중에 테이블이 리사이즈(2배 확장 / 절반 축소)될 때 **버킷 번호의 의미가 바뀌어** 키를 놓치거나 엉뚱한 곳을 가리킵니다.

### 어떻게 동작하나

```
GET /scan?cursor=0&count=100&prefix=user:
 → { "cursor": 8, "keys": ["user:3", …] }        돌려받은 cursor 로 다음 호출
GET /scan?cursor=8&count=100&prefix=user:
 → { "cursor": 0, "keys": [ … ] }                cursor 가 0 으로 돌아오면 끝
```

**핵심 아이디어: 커서를 1씩 올리지 않고 "비트를 뒤집은 값"을 1 올린다** (Redis `SCAN` 과 같은 방식, *역순 이진 증가 커서*).

용량이 16이면 버킷 번호가 4비트이고, 방문 순서는 이렇게 됩니다.

```
일반 순서   : 0, 1, 2, 3, 4, 5, 6, 7, 8, …
역순 이진   : 0, 8, 4, 12, 2, 10, 6, 14, 1, 9, 5, 13, 3, 11, 7, 15
              (0000, 1000, 0100, 1100, 0010, 1010, …)  ← 상위 비트부터 증가
```

한 칸 전진하는 계산 (`hashtable.js`):

```
v = 현재 커서
v = 마스크 바깥 비트를 전부 1 로 채움
v = 비트 뒤집기 → +1 → 다시 비트 뒤집기
```

**왜 이게 리사이즈에 안전한가**

해시 테이블의 버킷 번호는 `hash & (용량 - 1)`, 즉 **해시의 하위 비트**입니다. 용량이 2배가 되면 하위 비트가 1개 더 쓰입니다.

- **확장 (예: 8 → 16칸):** 옛 버킷 `i` 의 키는 새 테이블에서 `i` 또는 `i + 8` 로 갈라집니다. 역순 이진 순서는 "하위 비트를 먼저 고정하고 상위 비트를 바꿔 가며" 방문하므로, 이미 지나친 옛 버킷 `i` 의 키는 **이미 반환된 것**이고, 아직 안 지나쳤다면 갈라진 두 버킷을 **모두 앞으로 방문**합니다. → 놓치지 않습니다. (이미 반환한 키가 확장된 테이블에서 다시 나올 수는 있어서 중복이 생깁니다.)
- **축소 (예: 16 → 8칸):** 합쳐진 버킷을 다시 방문할 수는 있지만(중복) 놓치지는 않습니다.

커서는 "마스크하지 않은 값"을 그대로 돌려주고, **다음 호출 때의 현재 용량으로** 마스크합니다. 그래서 호출 사이에 용량이 바뀌어도 커서 값이 여전히 의미를 가집니다.

**보장과 비보장**

| | |
|---|---|
| 보장 | 순회를 **시작해서 끝낼 때까지 계속 존재한 키는 최소 한 번** 나옵니다 (리사이즈가 있어도) |
| 비보장 | 리사이즈가 있었다면 **같은 키가 두 번** 나올 수 있습니다 |
| 비보장 | 순회 도중에 새로 추가·삭제된 키는 나올 수도, 안 나올 수도 있습니다 |

**`count` 와 `prefix` 를 쓸 때 주의**

- `count` 는 **"한 번에 검사할 엔트리 수"** 이지 "돌려줄 개수"가 아닙니다 (1~10,000).
- `prefix` 로 거르면 한 페이지가 **비어 있어도** `cursor` 가 0 이 아니면 아직 끝나지 않은 것입니다. 계속 호출해야 합니다.
- 순회 중에 만난 **만료된 키는 그 자리에서 정리**하고 결과에서 뺍니다 (lazy expiration).
- SCAN 은 키를 "사용"한 것으로 치지 않으므로 **LRU 순서를 바꾸지 않습니다.**

**만료 청소(active expiration)도 같은 `scan`을 씁니다.** 1초마다 도는 `sweep()` 이 사용하던 증분 순회가 같은 함수라서, 이 개선으로 만료 청소도 리사이즈 도중에 안전해졌습니다.

클라이언트에서는 `for await` 로 편하게 돌 수 있습니다.

```js
for await (const key of cache.scanKeys({ prefix: 'user:', count: 100 })) {
  console.log(key);
}
```

### 한계
- 리사이즈가 끼면 같은 키가 중복으로 나옵니다 (호출자가 `Set` 으로 걸러야 함).
- 호출과 호출 사이에는 다른 요청이 끼어들므로, 전체가 **하나의 스냅샷은 아닙니다.** 한 번의 호출 안에서만 일관됩니다.
- `prefix` 필터는 서버가 걸러 주지만 **검사 자체는 전체 버킷을 돌아야** 하므로, 접두사에 맞는 키가 드물수록 빈 페이지가 많이 나옵니다.
- 무효화(`invalidate` 의 `prefix` / `all`)는 아직 한 번에 처리합니다. SCAN 으로 키를 모아 나눠 지우는 식으로 확장할 수 있지만 이번 범위에는 넣지 않았습니다.

## 3. 트랜잭션 (`POST /transaction`)

### 없으면 생기는 문제
이체(계좌 A에서 10 빼고 B에 10 더하기)를 요청 2개로 나눠 보낸다고 하겠습니다.

```
요청 1: incr acct:a -10         (A: 1000 → 990)
        ──── 이 순간 다른 클라이언트가 두 계좌를 읽으면 합계가 990 ────
요청 2: incr acct:b +10         (B: 0 → 10)
```

- **중간 상태가 관찰된다.** 합계가 1000이어야 하는데 990으로 보입니다.
- **중간에 끊기면 반쪽짜리 이체가 된다.** 요청 1만 성공하고 클라이언트나 네트워크가 죽으면 돈이 사라집니다.

실제로 `npm run demo:tx` 로 재현하면 **읽기 300번 중 160번**에서 합계가 틀리게 보였습니다(예: 980). 트랜잭션으로 보내면 **0번**이었습니다.

### 어떻게 동작하나

명령 여러 개를 **한 요청에 담아** 보내면, 서버가 다른 요청이 끼어들지 못하게 연달아 실행합니다.

```
POST /transaction
{ "commands": [
    { "cmd": "incr", "key": "acct:a", "by": -10 },
    { "cmd": "incr", "key": "acct:b", "by": 10 }
] }
 → { "results": [ {ok:true, value:990}, {ok:true, value:10} ] }
```

**왜 락이 필요 없나.** 모든 명령이 동기 함수이고, 트랜잭션도 "동기 함수 여러 개를 하나의 동기 함수 안에서 연달아 호출"하는 것이기 때문입니다. 이벤트 루프는 이 함수가 끝날 때까지 다른 요청을 실행하지 않습니다. 3장의 "명령이 원자적"이라는 성질이 "명령 묶음이 원자적"으로 자연스럽게 넓어진 것입니다.

**지원 명령:** `set` `get` `del` `exists` `incr` `ttl` `expire` `persist` `invalidate`

(`set` 은 `nx` / `xx` / `ttl` / `tags` 를 지원합니다. `mset` 과 달리 항목별로 성공/실패가 갈려도 되는 모델이기 때문입니다.)

**두 단계로 실행합니다.**

```
1단계  사전 검증   모든 명령의 형식을 먼저 검사 (모르는 cmd, 잘못된 key/ttl/by, 잘못된 invalidate 기준 …)
                   하나라도 틀리면 → 아무것도 실행하지 않고 400  ("commands[1]: unknown command: nope")
2단계  연속 실행   명령을 순서대로 실행. 앞 명령의 결과를 뒤 명령이 봄 (incr 하고 get 하면 증가된 값이 보임)
```

**실행 중 오류는 롤백하지 않습니다.** (Redis `MULTI/EXEC` 와 같은 모델)

```
{ cmd: set  key: a  value: 1 }       → { ok: true,  stored: true }
{ cmd: incr key: s }  (s = "text")   → { ok: false, error: { code: "WRONG_TYPE", … } }   ← 이 명령만 실패
{ cmd: incr key: a }                 → { ok: true,  value: 2 }                           ← 나머지는 계속 실행
```

롤백이 없는 이유: 정수가 아닌 값에 `incr`, 공간 부족 같은 오류는 **실행해 봐야 알 수 있어서** 사전 검증으로 막을 수 없습니다. 실행 도중 되돌리려면 변경 이력을 모두 기록해야 하는데, 이 모델은 대신 "형식 오류는 사전에 막고, 격리(끼어들기 없음)만 보장"하는 단순한 계약을 택했습니다. HTTP 응답은 일부 명령이 실패해도 **200** 이고, 실패는 `results[i].ok` 로 구분합니다.

**AOF: 한 줄로 기록해 "전부 아니면 전무"로 복구합니다.**

실행 중 발생한 모든 변경 레코드를 모아 두었다가 끝나면 **한 줄**로 기록합니다.

```
{"o":"t","r":[ {"o":"p","k":"acct:a","v":990,…}, {"o":"p","k":"acct:b","v":10,…} ]}
```

- 명령마다 따로 한 줄씩 쓰면, 크래시 시점에 **트랜잭션의 절반만** 복구될 수 있습니다.
- 한 줄은 "온전히 기록됐거나, 쓰다 만 줄(복구 때 통째로 버려짐)" 둘 중 하나입니다. 이미 있던 "마지막 줄이 쓰다 만 경우 버린다"는 크래시 복구 규칙이 그대로 트랜잭션의 원자성이 됩니다.
- 재시작 때 `{"o":"t"}` 레코드는 안의 레코드를 순서대로 재생합니다.
- **변경이 없는** 트랜잭션(읽기 명령만)은 아무것도 기록하지 않고, 변경이 **하나뿐이면** 감싸지 않고 일반 레코드 한 줄로 기록합니다.
- 실행 중 실패한 명령은 상태를 바꾸지 않았으므로 기록되지 않습니다.
- 트랜잭션 안에서 일어난 LRU 축출·무효화도 함께 기록되어 재시작 후에도 일관됩니다.

**클라이언트 사용법**

```js
const [stored, counter, value, failed] = await cache
  .multi()
  .set('a', 1, { ttl: 30 })
  .incr('counter')
  .get('a')
  .incr('some-text-key')        // 정수가 아니라서 실패
  .exec();                      // exec() 를 호출할 때 비로소 서버로 전송

// stored = true, counter = 1, value = 1, failed = MiniRedisHttpError (code: 'WRONG_TYPE')
```

결과는 명령 순서대로 돌아오고, 실패한 명령 자리에는 `MiniRedisHttpError` 객체가 들어갑니다. 형식이 잘못된 명령이 있으면 `exec()` 자체가 throw 하고 아무것도 실행되지 않습니다.

### 테스트로 확인한 것 (`test/batch-http.test.js`)
- 100개의 트랜잭션이 각각 같은 카운터를 두 번 올려도, 한 트랜잭션의 두 `incr` 결과는 항상 연속(`b = a + 1`)이고 최종값은 정확히 200
- 이체 트랜잭션 200개가 진행되는 동안 `mget` 200번이 모두 합계 1000을 관찰
- 겹치는 키를 쓰는 `mset` 100개가 동시에 와도 한 요청의 값만 남고 섞이지 않음
- 쓰다 만 트랜잭션 줄은 통째로 버려짐 (`test/batch-aof.test.js`)

### 한계
- **롤백이 없습니다.** 실행 중 오류가 난 명령 앞의 변경은 되돌려지지 않습니다.
- **낙관적 락(`WATCH`)이 없습니다.** "값을 읽고 → 클라이언트에서 판단하고 → 쓰기"는 두 요청에 걸치므로 원자적이지 않습니다. 이런 로직은 `incr`, `SET NX` 같은 **단일 명령**으로 만들거나, 판단까지 서버 명령 안에 넣어야 합니다.
- Redis처럼 `MULTI` 로 세션을 열어 두고 명령을 하나씩 쌓는 방식이 아니라, **한 요청에 명령을 모두 담는** 방식입니다 (HTTP가 요청 단위라서).
- 명령은 최대 1,000개이고 본문은 1MB 이하입니다. 안에 `invalidate` 의 `prefix` / `all` 처럼 O(n) 명령을 넣으면 그동안 다른 요청이 모두 대기합니다.
- 기능은 지정된 9개 명령으로 한정됩니다 (`keys`, `mget` 등은 넣지 않았습니다).

## 4. 세 기능이 맞물리는 방식

```
 mget / mset ──┐
               ├─▶ 모두 "동기 함수 하나 안에서 끝까지" 실행 ──▶ 끼어들기 없음 (락 불필요)
 transaction ──┘                                              └▶ 변경은 AOF 에 한 줄 ({"o":"t"})

 scan ─────────▶ 해시 테이블의 증분 순회 (역순 이진 커서) ─▶ 만료 청소(sweep) 와 공유
```

- 배치와 트랜잭션은 **같은 방식**(검증 → 동기 실행 → AOF 한 줄)으로 원자성을 얻습니다. 차이는 `mset` 은 "전부 성공 아니면 전부 거부"이고, 트랜잭션은 "형식 오류는 전부 거부, 실행 중 오류는 부분 실패"라는 점입니다.
- 셋 다 한 번에 처리하는 양에 상한(`MAX_BATCH`, SCAN 은 `count` 최대 10,000)을 둡니다. **단일 스레드에서는 한 요청이 오래 걸리면 모든 요청이 기다리기 때문**입니다.
- 어떤 걸 쓸까: 여러 키를 읽거나 쓰기만 하면 → `mget` / `mset`. 그 사이에 계산이나 조건이 필요하면 → 트랜잭션. 키를 훑어봐야 하면 → `SCAN`.
