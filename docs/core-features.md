# 핵심 기능 설명: 왜 필요하고, 어떻게 동작하나

Mini Redis 에 넣은 다섯 가지 기능(만료 · 무효화 · 동시성 · AOF · LRU)을 각각
**① 없으면 어떤 문제가 생기는지 → ② 어떻게 동작하는지 → ③ 한계** 순서로 설명합니다.
코드 위치는 `src/` 기준입니다.

| 기능 | 없으면 | 해결 방식 | 코드 |
|---|---|---|---|
| 만료(TTL) | 낡은 값이 영원히 남고 메모리가 계속 늘어남 | lazy + active expiration | `store.js` `#live`, `sweep` |
| 무효화 | 원본이 바뀌어도 낡은 캐시를 계속 응답 | key / tag / prefix / all 단위 즉시 폐기 | `store.js` `invalidate` |
| 동시성 | 동시 요청에서 값이 유실되거나 꼬임 | 단일 스레드 + 동기(원자적) 명령 | `store.js` 전체, `server.js` |
| AOF | 서버가 재시작되면 데이터가 전부 사라짐 | 변경 명령을 로그에 기록, 재시작 때 재생 | `aof.js` |
| LRU | 메모리가 무한히 늘거나, 가득 차면 새 데이터를 못 넣음 | 가장 오래 안 쓴 키부터 축출 | `store.js` `#lru*` |

---

## 1. 만료 (TTL, Time To Live)

### 없으면 생기는 문제
- **낡은 데이터가 영원히 응답된다.** 상품 가격을 캐시했는데 원본이 바뀌어도 캐시는 그대로입니다. 삭제하는 코드를 따로 안 짜면 "언제까지 믿어도 되는지"가 없습니다.
- **메모리 누수.** 한 번 쓰고 다시는 안 읽는 키(예: 일회성 인증 코드, 세션)가 쌓이기만 합니다.
- **임시 키를 만들 수 없다.** "5분 동안만 유효한 락", "1분에 10번까지만 허용하는 카운터" 같은 패턴이 불가능합니다.

### 어떻게 동작하나
키마다 `expiresAt`(**절대 시각**, ms)을 저장하고, 두 가지 방식으로 정리합니다.

**① Lazy expiration (읽을 때 확인)**

```
GET user:1
  → 해시 테이블에서 엔트리를 찾음
  → expiresAt <= 지금 ?
       예 → 그 자리에서 삭제하고 "없음"(404) 으로 응답     ← 만료된 값은 절대 응답으로 나가지 않는다
       아니오 → 값을 반환
```

get 뿐 아니라 exists / ttl / incr / expire / del / `SET NX` 판정 등 **키에 접근하는 모든 경로**가 `#live()` 를 거치므로 만료된 키는 어디서도 "있는 키"로 취급되지 않습니다.

**② Active expiration (주기적 청소)**

Lazy 만으로는 "아무도 안 읽는 만료 키"가 남습니다. 그래서 1초마다 `sweep()` 이 실행됩니다.

```
sweep():
  해시 테이블을 scan(cursor, 200) 으로 200개씩만 훑음   ← 한 번에 전체를 보면 서버가 멈추므로 조금씩
  만료된 키 삭제
  검사한 키의 25% 넘게 만료였다면 → 만료 키가 많다는 뜻이니 바로 한 번 더 (최대 5회)
```

**경계값:** `expiresAt <= now` 이면 만료입니다. TTL 1000ms 로 저장하면 정확히 1000ms 시점에 이미 만료입니다.

**덮어쓰기:** `SET` 으로 값을 덮어쓰면 이전 TTL 은 사라집니다 (TTL 을 안 주면 만료 없음). `INCR` 은 TTL 을 유지합니다.

### 왜 "절대 시각"으로 저장하나
"60초 뒤"로 저장하면 AOF 로 복원할 때 재시작 시점부터 다시 60초가 시작됩니다. 절대 시각이면 **서버가 꺼져 있던 시간도 흐른 것으로 계산**되어, 꺼져 있는 동안 만료된 키가 되살아나지 않습니다.

### 한계
- Active 청소는 주기적이라 만료 직후 최대 약 1초간 메모리에 남을 수 있습니다 (응답에는 나가지 않음).
- 시계가 거꾸로 가면(시스템 시간 변경) 만료 판정이 어긋날 수 있습니다.

## 2. 무효화 (Invalidation)

### 없으면 생기는 문제
- **TTL 만 쓰면 TTL 이 끝날 때까지 낡은 값이 나간다.** TTL 60초로 캐시한 상품 가격을 수정해도 최대 60초 동안 옛 가격이 응답됩니다. 결제·재고처럼 틀리면 안 되는 데이터에는 치명적입니다.
- **"관련된 키를 전부" 지우기 어렵다.** 카테고리 `c1` 의 상품 캐시 수백 개를 지우려면 키 목록을 호출자가 다 알고 하나씩 `DEL` 해야 합니다. 하나라도 빼먹으면 낡은 데이터가 남습니다.

### 어떻게 동작하나
`DEL` 은 "키 하나 삭제", 무효화는 **"원본이 바뀌어 믿을 수 없게 된 캐시를 기준 단위로 한 번에 폐기"** 하는 기능입니다.

| 기준 | 요청 예 | 동작 | 비용 |
|---|---|---|---|
| `key` | `{"key":"product:7"}` | 키 하나 삭제 | O(1) |
| `tag` | `{"tag":"category:c1"}` | 해당 태그가 붙은 키 전부 | O(해당 키 수) |
| `prefix` | `{"prefix":"product:"}` | 접두사가 같은 키 전부 | O(n) 전체 순회 |
| `all` | `{"all":true}` | 전부 | O(n) |

**태그의 동작.** 저장할 때 `tags` 를 붙여 두면 `태그 → 키 집합` 보조 인덱스가 같이 만들어집니다.

```
PUT /keys/product:1  {"value":…, "tags":["category:c1"]}
PUT /keys/product:6  {"value":…, "tags":["category:c1"]}

tagIndex:  "category:c1" → { product:1, product:6 }

POST /invalidate {"tag":"category:c1"}
  → tagIndex 에서 키 집합을 바로 꺼내 그 키들만 삭제   (전체 테이블을 훑지 않는다)
```

키가 삭제·덮어쓰기·만료되면 태그 인덱스에서도 같이 빠집니다 (찌꺼기가 남지 않음).

**안전장치:**
- 기준은 **정확히 하나만** 받습니다. `{key, tag}` 처럼 둘을 같이 보내면 400. 실수로 범위가 넓어지는 것을 막습니다.
- 이미 만료된 키는 무효화 개수에 세지 않습니다.
- 무효화 직후 같은 키를 조회하면 반드시 404 입니다 (테스트에서 50회 반복 검증).
- AOF 가 켜져 있으면 삭제로 기록되어 재시작 후에도 되살아나지 않습니다.

### TTL 과 무효화의 역할 분담

| | TTL | 무효화 |
|---|---|---|
| 폐기 시점 | 시간이 지나서 (자연스럽게) | 이벤트가 발생해서 (즉시) |
| 누가 결정 | 저장하는 쪽이 미리 | 원본을 바꾸는 쪽이 그때그때 |

함께 쓰는 것을 권장합니다. 무효화 호출이 어딘가에서 누락돼도 **TTL 이 최후의 안전망**이 됩니다.

### 한계
- `prefix` / `all` 은 전체 순회라 키가 아주 많으면 오래 걸립니다 (그동안 다른 요청이 대기).
- 무효화는 "저장소 안의 캐시"만 지웁니다. 이미 클라이언트나 다른 계층(CDN 등)이 받아간 값은 지울 수 없습니다.

## 3. 동시성

### 없으면 생기는 문제
요청 1,000개가 동시에 들어오는 서버를 가정합니다. 값을 읽고 → 계산하고 → 쓰는 사이에 다른 요청이 끼어들 수 있다면:

**① 갱신 유실 (lost update)** — 카운터 `INCR` 예

```
요청 A: 값 읽음 (10)
요청 B: 값 읽음 (10)          ← A 가 쓰기 전에 읽음
요청 A: 11 을 씀
요청 B: 11 을 씀              ← 12 여야 하는데 11. 한 번의 증가가 사라짐
```

**② 조건부 저장이 깨진다** — "없을 때만 저장(`SET NX`)"으로 락을 구현했는데, 둘 다 "없다"고 판단하고 둘 다 저장하면 **락을 두 명이 동시에 잡게 됩니다.**

**③ 찢어진 값(torn read)** — 쓰는 도중에 읽으면 반쯤 바뀐 객체가 보일 수 있습니다.

### 어떻게 동작하나
Redis 와 같은 **"단일 스레드 + 원자적 명령"** 모델입니다.

1. **모든 명령은 `await` 가 없는 동기 함수**입니다 (`MiniRedis.set/get/incr…`).
2. Node.js 이벤트 루프는 한 번에 하나의 콜백만 실행하므로, 동기 함수가 끝나기 전에 **다른 요청이 끼어들 수 없습니다.**
3. 그래서 락(mutex) 없이도 읽기→계산→쓰기가 하나의 덩어리로 실행됩니다.

```
  네트워크 (비동기, 여러 요청이 동시에 도착)
      │  본문 수신 완료
      ▼
  ┌─────────────────────────────┐
  │  store.incr('counter')       │   ← 이 안에서는 다른 요청이 절대 끼어들 수 없음
  │  읽기 → +1 → 쓰기 → AOF 기록  │
  └─────────────────────────────┘
      ▼
  응답 전송 (비동기)
```

- 네트워크 I/O 는 비동기로 받고, **요청 본문이 완전히 도착한 뒤에** 명령만 동기 실행합니다 (`server.js`).
- AOF 쓰기도 `writeSync` 라서 **실행 순서 = 로그 순서**입니다.
- 저장·조회 시 값을 **복사**하므로, 호출자가 나중에 객체를 수정해도 저장소 내부가 오염되지 않습니다.
- 클라이언트의 `getOrSet` 은 **single-flight** 로 같은 키의 동시 miss 를 하나로 합칩니다 (cache stampede 방지). 이 부분은 서버가 아닌 클라이언트 쪽 동시성 대책입니다.

### 테스트로 확인한 것 (`test/server.test.js`)
- 동시 `INCR` 500개 → 최종값 정확히 500, 반환값 1~500 이 전부 유일
- 동시 `SET NX` 100개 → 정확히 1명만 성공, 99명은 409
- 같은 키에 PUT·GET·DELETE 를 섞어 300라운드 → 찢어진 값 없음

### 한계
- **CPU 코어 1개만 사용**합니다. 명령 하나가 오래 걸리면(예: `prefix` 무효화) 그동안 모든 요청이 대기합니다.
- 확장하려면 키 해시로 샤딩한 여러 프로세스(Redis Cluster 방식)가 필요하고, 그때는 여러 키에 걸친 원자성이 어려워집니다.
- 이 보장은 "저장소 안의 명령"에 대한 것입니다. 호출자가 `GET` 후 계산하고 `PUT` 하는 식으로 **두 요청에 걸쳐** 만든 로직은 원자적이지 않습니다. 그런 용도에는 `INCR`, `SET NX` 처럼 한 명령으로 끝나는 연산을 써야 합니다.

## 4. AOF (Append-Only File) 영속성

### 없으면 생기는 문제
- **프로세스가 죽거나 재시작하면 데이터가 전부 사라진다.** 메모리는 휘발성입니다. 배포 한 번, 크래시 한 번에 모든 캐시가 비워집니다.
- **콜드 스타트 폭풍.** 캐시가 갑자기 비면 모든 요청이 한꺼번에 DB 로 몰려 DB 가 과부하로 쓰러질 수 있습니다. 캐시가 DB 를 보호하던 구조가 반대로 장애의 방아쇠가 됩니다.
- 캐시가 아니라 **카운터·세션·락 같은 상태 데이터**를 담으면 유실이 곧 데이터 손실입니다.

### 어떻게 동작하나
**데이터를 바꾸는 명령을 파일 끝에 계속 덧붙이고, 재시작하면 처음부터 재생(replay)** 해서 메모리를 복원합니다.

**로그 형식** — 한 줄에 JSON 하나:

```
{"o":"p","k":"user:1","v":{"name":"kim"},"e":1789000000000,"t":["user"]}   저장 (put)
{"o":"d","k":"user:1"}                                                    삭제 (delete)
{"o":"f"}                                                                 전체 비우기 (flush)
```

`e` 는 만료 **절대 시각**입니다 (1장 참고). `INCR`, `EXPIRE`, `PERSIST`, 무효화, LRU 축출도 모두 위 세 종류 레코드로 기록됩니다.

**재시작 시:**

```
파일을 위에서부터 한 줄씩 읽음
  put    → 만료 시각이 이미 지났으면 복원하지 않음, 아니면 메모리에 넣음
  delete → 삭제
  flush  → 전체 비움
→ 로그를 다 재생하면 종료 직전과 같은 상태
```

**fsync 정책** (`FSYNC` 환경변수) — "write 했다"와 "디스크에 확실히 박혔다"는 다릅니다. write 는 OS 캐시에 먼저 가고 fsync 가 디스크로 내려보냅니다.

| 정책 | 동작 | 장단점 |
|---|---|---|
| `always` | 쓰기마다 fsync | 가장 안전, 가장 느림 |
| `everysec` (기본) | 1초마다 fsync | 정전 시 최대 약 1초 분량 유실 가능 |
| `no` | OS 에 맡김 | 가장 빠름, 유실 폭 큼 |

**프로세스만 죽는 경우(`kill -9`)** 는 이미 `write` 된 데이터가 OS 캐시에 있으므로 어느 정책이든 보존됩니다 (테스트로 검증). fsync 정책이 영향을 주는 것은 **OS 나 전원이 꺼지는 경우**입니다.

**손상 대응:**
- 마지막 줄이 쓰다 만 상태(전원 차단 등) → 버리고 파일을 잘라낸 뒤 이어씀
- 중간에 깨진 줄 → 그 줄만 건너뛰고 나머지를 복구
- 알 수 없는 레코드 종류 → 무시 (상위 버전 로그와 호환)

**Compaction (로그 압축)** — 로그는 계속 길어집니다. `INCR` 을 2,000번 하면 로그 2,000줄이지만 살아있는 키는 1개입니다.

```
현재 살아있는 키만 새 임시 파일(.tmp)에 씀 → fsync → rename 으로 원자적 교체
```

로그가 살아있는 키 수의 2배(최소 1만 줄)를 넘으면 자동으로 실행됩니다. `rename` 은 원자적이라 **도중에 죽어도 옛 파일이 그대로 남습니다.** 만료된 키는 압축 때 버려집니다.

### 한계
- `everysec` 에서는 OS 크래시 시 최대 약 1초 분량이 유실될 수 있습니다.
- 쓰기와 compaction 이 **동기 I/O** 라 그 순간 이벤트 루프가 잠깐 멈춥니다. `always` 는 특히 느립니다.
- 복제(replication)가 없어서 서버 한 대가 죽으면 복구되는 동안은 서비스가 중단됩니다.
- **읽기 기록은 로그에 없습니다.** LRU 를 쓸 때 재시작 후 순서는 "마지막으로 쓴 순서"로 복원됩니다.

## 5. LRU 축출 (Least Recently Used)

### 없으면 생기는 문제
저장소에는 결국 상한이 필요합니다. 상한이 없거나 가득 찼을 때의 동작이 없으면:

- **상한이 없으면(기본 `MAX_KEYS` 무제한)** 키가 계속 쌓여 프로세스가 메모리를 다 쓰고 OOM 으로 죽습니다. 캐시가 서비스 전체를 죽이는 셈입니다.
- **상한만 있고 축출이 없으면(`noeviction`)** 가득 찬 순간부터 새 키가 전부 거부(507)됩니다. 정작 지금 필요한 새 데이터는 못 넣고, **예전에 한 번 쓰고 안 읽는 데이터가 자리를 차지**합니다. 캐시 적중률이 시간이 갈수록 나빠집니다.

### 어떻게 동작하나
가득 차면 **"가장 오래 사용되지 않은 키"를 버리고** 새 키를 받습니다. 최근에 쓴 것은 앞으로도 쓸 가능성이 높다는 가정입니다 (시간 지역성).

**구조: 해시 테이블 + 이중 연결 리스트**

```
해시 테이블   key ──▶ entry                      "찾기" 담당 — O(1)

이중 연결 리스트   head ⇄ entry ⇄ entry ⇄ entry ⇄ tail
                  (가장 최근)                   (가장 오래됨 = 축출 대상)
                                                 "사용 순서" 담당 — 갱신/제거 O(1)
```

두 구조를 합치는 이유는 이렇습니다.
- 해시 테이블만 있으면 "가장 오래된 것"을 찾으려고 전체를 훑어야 합니다 (O(n)).
- 리스트만 있으면 키를 찾으려고 전체를 훑어야 합니다 (O(n)).
- 해시 테이블이 **리스트 노드를 직접 가리키므로** 찾은 뒤 리스트에서 떼어 head 로 옮기는 것이 포인터 몇 개만 바꾸는 O(1) 입니다.

**동작 흐름:**

```
키에 접근 (get / set / incr / expire / ttl …)
  → 엔트리를 리스트에서 떼어 head 로 이동       "방금 썼다"

새 키 저장 시 size >= MAX_KEYS 이면:
  1. 만료된 키부터 정리   (이미 죽은 데이터를 먼저 버림. 살아있는 키를 버리기 전에)
  2. 그래도 가득이면 tail 의 엔트리를 삭제 (AOF 에는 삭제로 기록)
  3. 새 키 저장
```

**설계 결정:**
- `keys()` 같은 관리용 순회와 만료 sweep 은 "사용"으로 치지 않습니다 (관리 행위가 순서를 오염시키지 않게).
- 덮어쓰기는 키 수가 늘지 않으므로 축출을 일으키지 않지만, 최근 사용으로는 갱신됩니다.
- 축출된 키는 태그 인덱스에서도 같이 지워집니다.
- 축출도 AOF 에 삭제로 기록되어 재시작 후 되살아나지 않습니다. `MAX_KEYS` 를 줄여서 재시작하면 시작할 때 맞춰서 축출합니다.
- 기본값은 `noeviction` 이라 켜지 않으면 기존 동작이 그대로입니다. `lru` 는 `MAX_KEYS` 가 반드시 필요합니다.

### 사용법

```bash
EVICTION=lru MAX_KEYS=1000 npm start
curl localhost:6380/stats    # "evicted": 축출된 횟수
```

### 한계
- **키 개수 기준**입니다. 값 하나가 1KB 든 1MB 든 똑같이 1로 셉니다 (바이트 단위 상한은 없음).
- 정확한 LRU 이지만, 한 번만 읽는 대량 스캔이 자주 쓰는 키를 밀어낼 수 있습니다 (LFU 같은 다른 정책은 없음).
- 읽기 기록이 AOF 에 없어서 재시작 직후에는 순서 정보가 부정확합니다.

## 6. 다섯 기능이 서로 맞물리는 방식

```
 저장 ──▶ [만료 시각 기록] ──▶ 해시 테이블 + 태그 인덱스 + LRU 리스트 ──▶ AOF 에 기록
                                      ▲                    │
          lazy 확인 / sweep / 무효화 / 축출                  └─ 삭제 계열은 모두 {"o":"d"} 로 기록
                                      │
                          (모두 한 스레드에서 동기로 실행 → 서로 끼어들지 않음)
```

- 만료·무효화·축출은 **삭제하는 이유만 다를 뿐** 모두 같은 `#remove()` 를 거칩니다. 그래서 해시 테이블, 태그 인덱스, LRU 리스트가 항상 함께 정리됩니다.
- 동시성 모델 덕분에 "삭제하면서 동시에 읽기" 같은 경합이 없어서, 위 구조들을 락 없이 일관되게 유지할 수 있습니다.
- AOF 는 이 모든 변경의 결과를 같은 순서로 기록합니다.
